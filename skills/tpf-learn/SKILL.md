# 점수 → 생성 최적화 · SOP 최적화

흐름: **평가(점수·태그·이유) → 고득점이 다음 생성의 참고가 됨 → 재료가 쌓이면 보완 제안 / 필요할 때 전체 재정리 → 운영자가 반영 → 되돌리기 가능**. 모든 평가·실행·SOP 변경은 GitHub data 브랜치와 구글 시트에도 저장됩니다.

## 1. 평가하기

- 운영자가 평가를 말하면 점수와 이유를 정리해 저장: `tpf rate <id> <step> <1-5> --tags 태그1,태그2 --note "이유"` (MCP `output_rate`)
  - 태그 후보: `tpf tags <step>` — 좋은 점(+)·아쉬운 점(−). 운영자 말에 맞는 태그를 고르고, 없으면 짧은 새 태그
  - 이유는 **구체적으로** ("마감일을 첫 문장에 둬서 훅이 셈" ○ / "좋음" ✕). 모호하면 무엇이 좋았는지 한 번 묻는다
  - 기준: ★5 그대로 쓸 만큼 최고 · ★4 좋음 · ★3 보통 · ★2 고칠 게 많음 · ★1 못 씀. ★2 이하는 아쉬운 점 태그나 이유가 필요
  - 같은 산출물에 다시 매기면 갱신된다(GitHub 등급 폴더도 이동)
- 산출물을 고친 뒤 승인하면 "수정 예"(AI 원본↔최종본)가 자동 저장된다
- 성과가 좋은 콘텐츠는 운영자와 확인 후 단계별로 `tpf rate … 5 --tags 성과우수 --note "신청 n건"`

## 2. 지금까지의 학습 확인

`tpf notes <step>` — 점수 현황, SOP 버전별 평균 점수, 점수를 올린/내린 조건(태그·특징), 반영·거절된 학습, 높은/낮은 점수 이유. **SOP 를 손대기 전에 반드시 읽는다.**

## 3. SOP 를 바꾸는 두 가지 방법

| 방법 | 명령 | 언제 |
|---|---|---|
| 보완 제안 (줄 단위) | `tpf learn <step> --propose` | 새 고득점 예시가 쌓였을 때 (자동으로도 생김) |
| 전체 재정리 | `tpf consolidate <step> [--instruction "…"]` | SOP 가 길어지고 겹칠 때, 몇 차례 보완이 쌓였을 때, 점수 추이가 정체될 때 |

둘 다 학습 노트를 읽고 만들어진다. 재정리안은 구조와 ## 금지 항목을 보존하도록 검사되고, 자동 반영되지 않는다.

## 4. 운영자에게 보여주기 (반영은 운영자 결정)

`tpf proposals <step> --status pending` 결과를 정리한다.
- 보완 제안: 번호·[추가/수정/삭제]·섹션·문구·근거 예시·⚠ 경고
- 재정리안: 요약 + changelog(통합·삭제·순서 변경과 이유) + 주요 차이 몇 줄
- 학습 노트의 점수 근거와 맞는지 내 의견을 덧붙인다 (근거가 약하거나 거절된 방향과 비슷하면 빼자고 제안)

## 5. 반영 / 거절 / 되돌리기

- 보완 제안: `tpf proposal apply <pid>` (일부만: `--only 0,1`, 문구 수정: MCP `sop_proposal_decide` 의 `edits`)
- 재정리안: `tpf proposal apply <pid>` (다듬은 md 로: `--file 파일.md`, 그 사이 SOP 가 바뀌었으면 `--force` 는 운영자 동의 시에만)
- 거절: `tpf proposal reject <pid> --note "이유"` — 이유는 다음 제안 때 AI 가 읽는다
- 되돌리기: `tpf proposal revert <pid>`
- 반영 후 효과는 다음 평가들의 "SOP 버전별 평균"으로 확인한다

## 하지 않는 것

- 운영자 확인 없이 `apply` 하지 않는다 (자동 모드가 이미 반영한 것은 예외)
- 사실 정확성·출처·금지 표현 규칙을 약하게 만드는 변경은 반영을 권하지 않는다
