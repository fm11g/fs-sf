# 좋은 결과물 → SOP 보완

흐름: **좋은 예 저장 → (재료가 쌓이면) 제안 생성 → 운영자가 골라 반영 → 필요하면 되돌리기**. 기존 SOP 는 통째로 바뀌지 않고, 줄 단위 추가·수정·삭제만 적용됩니다.

## 1. 학습 재료 모으기

- 운영자가 "이거 좋다/잘 됐다"고 하면 이유를 한 줄로 정리해 저장: `tpf good <id> <step> --note "좋은 이유"` (MCP `exemplar_mark`)
  - 이유는 **구체적으로**: "숫자를 첫 문장에 둬서 훅이 셈" ○ / "좋음" ✕. 운영자 말에서 근거를 뽑고, 모호하면 무엇이 좋았는지 한 번 묻는다
- "별로다/이건 아니다" → `tpf bad <id> <step> --note "아쉬운 점"` (메모 필수)
- 운영자가 산출물을 직접 고친 뒤 승인하면 "수정 예"가 자동 저장된다 (따로 할 일 없음)
- 성과 기준으로 고를 때: `tpf metrics` 에서 전환이 높은 콘텐츠를 운영자와 확인한 뒤 단계별로 `tpf good … --note "성과: 신청 n건"`

## 2. 제안 만들기

- `tpf learn` 로 단계별 재료 개수와 `should_propose` 확인
- `tpf learn <step> --propose` — AI 가 좋은 예의 공통점을 찾아 SOP 대비 변경안을 만든다 (20~60초)
- 학습 방식이 `auto` 면 근거 2개 이상인 추가·수정은 바로 반영되고, 삭제·금지 항목 변경은 제안으로 남는다

## 3. 운영자에게 보여주기 (반영은 운영자 결정)

`tpf proposals <step> --status pending` 결과를 이렇게 정리한다.

```
제안 #12 · 02 기획 — (요약 1~2문장)
0. [추가] 집중 포인트: 마감 있는 공고는 "이번 주 마감" 훅 1순위   (근거 #31 #34 #40)
1. [수정] 집중 포인트: "6~8장면" → "6~7장면"                       (근거 #31 #40)
2. [삭제] 금지: …  ⚠ 금지 항목 삭제 — 권장하지 않음
```
- ⚠ 경고(금지 항목 변경, 근거 1개, 형식 규칙)는 반드시 함께 말한다
- 내 의견도 덧붙인다: 근거가 약하거나 기존 지침과 충돌하는 항목은 빼자고 제안

## 4. 반영 / 거절 / 되돌리기

- 전부: `tpf proposal apply <pid>` · 일부: `--only 0,1` · 문구를 고쳐서: MCP `sop_proposal_decide` 의 `edits` ({"0": "새 문구"})
- 거절: `tpf proposal reject <pid> --note "이유"` — SOP 는 그대로
- 되돌리기: `tpf proposal revert <pid>` (그 뒤 SOP 를 또 고쳤다면 관리자 SOP 변경 이력에서 복원)
- 반영 후 `tpf sop get <step>` 으로 바뀐 줄을 보여준다

## 하지 않는 것

- 운영자 확인 없이 `apply` 하지 않는다 (자동 모드가 이미 반영한 것은 예외)
- 사실 정확성·출처·금지 표현 규칙을 약하게 만드는 변경은 반영을 권하지 않는다
